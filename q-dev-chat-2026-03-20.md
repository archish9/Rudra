# RudraAnvil Project Flow Explanation

## **Command Execution Flow**

When a user enters a command like `rudraanvil build "Create a FastAPI app"`, here's what happens:

### **1. Entry Point (pyproject.toml)**
```
[project.scripts]
rudraanvil = "rudraanvil.cli:app"
```
This maps the `rudraanvil` command to the Typer CLI app in `cli.py`.

### **2. CLI Layer (cli.py)**
- Parses command (build/chat/fix/edit/review/suggest/resume/watch)
- Validates arguments and options
- Gets project path (defaults to current directory)
- Prompts for project context if missing (language, framework, database)
- Creates the main agent via `create_main_agent()`

### **3. Agent Creation (main_agent.py)**
The `create_main_agent()` function:
- Initializes **VirtualFileSystem** (loads existing project files)
- Creates **CheckpointManager** (for saving/resuming sessions)
- Builds **system prompt** based on command type
- Configures **Ollama LLM** (ChatOllama with gpt-oss:20b model)
- Creates **deepagents** agent with:
  - Custom tools (planning, file operations)
  - FilesystemBackend (writes to actual disk)
  - Subagent configuration (general-purpose code writer)

### **4. Agent Execution (RudraAnvilAgent.run())**
- Streams execution in real-time
- Logs tool calls and responses
- Monitors for errors and loops
- Tracks file changes (created/modified)
- Returns AgentResult with summary

## **Tools Executing During Build Command**

### **Main Agent Tools:**
1. **update_plan(plan_markdown)** - Creates task checklist in `.rudraanvil/PLAN.md`
2. **read_plan()** - Reads current plan
3. **list_directory(path)** - Lists files/folders
4. **read_file(path)** - Reads file content
5. **edit_file(path, old, new)** - Edits existing files (used to check off plan items)
6. **task(subagent_type, instructions)** - Spawns subagent (deepagents built-in)

### **Subagent Tools (general-purpose):**
1. **write_file(path, content)** - Creates new files
2. **edit_file(path, old, new)** - Modifies existing files
3. **read_file(path)** - Reads files
4. **list_directory(path)** - Lists directory contents

### **Backend (FilesystemBackend):**
- Writes all file operations to actual disk at `project_path`
- Anchors paths to project root (virtual_mode=True)
- Prevents absolute path escapes

---

## **Key Design Patterns**

1. **Supervisor-Worker Pattern**: Main agent plans and delegates to subagents
2. **Filesystem-Based Context**: Plan stored in `.rudraanvil/PLAN.md` instead of LLM memory
3. **Real-time Streaming**: Uses `astream()` for live progress updates
4. **Error Recovery**: Detects tool failures and consecutive errors
5. **Checkpoint System**: Saves state for resume functionality
6. **Virtual Filesystem**: Tracks changes before syncing to disk

This architecture allows the agent to handle complex multi-file projects while maintaining context efficiency and providing transparent execution visibility.

# State Folder Files Explained

The `state/` folder manages **persistence, session recovery, and project context** for RudraAnvil. Here's what each file does:

---

## **1. checkpoint.py** - Session Persistence & Resume

### Purpose
Saves the agent's complete state to disk so you can **resume interrupted sessions** later.

### Key Components

#### **Checkpoint (dataclass)**
A snapshot of the agent's state at a point in time:

```python
@dataclass
class Checkpoint:
    session_id: str              # Unique ID (12-char hash)
    created_at: str              # ISO timestamp
    updated_at: str              # Last modified timestamp
    
    # What the agent is working on
    task_description: str        # Original user task
    todo_list: dict              # Serialized TodoList
    
    # File system state
    virtual_fs: dict             # All files in memory
    
    # Agent's conversation history
    agent_memory: list[dict]     # LLM messages
    
    # Sub-agent states (if any spawned)
    sub_agent_states: dict
    
    # Progress tracking
    iterations_completed: int
    files_created: list[str]
    files_modified: list[str]
```

#### **CheckpointManager**
Manages saving/loading checkpoints:

| Method | Purpose |
|--------|---------|
| `create(task)` | Creates new checkpoint with auto-generated session ID |
| `save(checkpoint)` | Writes checkpoint to `.rudraanvil/checkpoint-{id}.json` |
| `load(session_id)` | Restores checkpoint from disk |
| `list_sessions()` | Lists all saved sessions with metadata |
| `delete(session_id)` | Removes a checkpoint |
| `update_todo_list()` | Updates todo list in current checkpoint |
| `update_virtual_fs()` | Updates file system state |
| `install_interrupt_handlers()` | Auto-saves on Ctrl+C |

### Usage Example
```python
# Create checkpoint
checkpoint_manager = CheckpointManager(Path(".rudraanvil"))
checkpoint = checkpoint_manager.create("Build FastAPI app")

# Save progress
checkpoint_manager.save()

# Resume later
checkpoint = checkpoint_manager.load("abc123def456")
```

### Storage Location
```
.rudraanvil/
├── checkpoint-abc123def456.json
├── checkpoint-xyz789ghi012.json
└── ...
```

## **2. todo.py** - Task Tracking System

### Purpose
Provides a **dynamic task list** that the agent uses to track work items. This is the **legacy/fallback system** - the new approach uses `.rudraanvil/PLAN.md` instead.

### Key Components

#### **TodoStatus (Enum)**
```python
class TodoStatus(str, Enum):
    PENDING = "pending"        # Not started
    IN_PROGRESS = "in_progress"  # Currently working
    COMPLETED = "completed"    # Done
    FAILED = "failed"          # Attempted but failed
    BLOCKED = "blocked"        # Waiting on something
```

#### **TodoItem (dataclass)**
A single task:

```python
@dataclass
class TodoItem:
    id: str                    # 8-char UUID
    title: str                 # "Create main.py"
    description: str           # Detailed instructions
    status: TodoStatus         # Current state
    priority: int              # Higher = more urgent
    parent_id: Optional[str]   # For subtasks
    created_at: str
    completed_at: Optional[str]
    assigned_agent: Optional[str]  # Which subagent is handling this
```

#### **TodoList**
Manages the collection of tasks:

| Method | Purpose |
|--------|---------|
| `add(title, description, priority)` | Add new task |
| `add_urgent(title)` | Add high-priority task at top |
| `get(item_id)` | Retrieve task by ID |
| `get_next_pending()` | Get highest priority pending task |
| `get_in_progress()` | List all active tasks |
| `get_completed()` | List finished tasks |
| `is_complete()` | Check if all tasks done |
| `summary()` | Generate text summary for LLM |

### Why It's Being Replaced
The README mentions:
> "CRITICAL: NEVER use write_todos — it bloats the context window. Always use update_plan instead."

The new system writes tasks to `.rudraanvil/PLAN.md` as markdown, which:
- Doesn't consume LLM context tokens
- Can be edited with standard file tools
- Is human-readable
- Persists across sessions

### Current Usage
Still used for:
- Display purposes in CLI (`/status` command)
- Checkpoint serialization
- Backward compatibility

## **3. project_config.py** - Tech Stack Context

### Purpose
Stores **project-specific configuration** so the agent knows what technologies to use (language, framework, database).

### Key Components

#### **ProjectContext (dataclass)**
```python
@dataclass
class ProjectContext:
    primary_language: str      # "Python", "TypeScript", "Go"
    framework: str             # "FastAPI", "Next.js", "Express"
    database: str              # "PostgreSQL", "MongoDB", "SQLite"
    additional_context: str    # Custom rules/architecture notes
```

#### **ProjectConfigManager**
Manages reading/writing config:

| Method | Purpose |
|--------|---------|
| `load()` | Reads `.rudraanvil/project.json` or returns empty context |
| `save(context)` | Writes context to disk |

### Usage Flow
1. **First run**: CLI prompts user for tech stack
2. **Saved to**: `.rudraanvil/project.json`
3. **Subsequent runs**: Auto-loaded, no prompts
4. **Injected into**: System prompt for agent

### Example Storage
```json
{
  "primary_language": "Python",
  "framework": "FastAPI",
  "database": "PostgreSQL",
  "additional_context": "Use async/await, follow REST conventions"
}
```

### Why This Matters
Without this, the agent might:
- Generate JavaScript when you want Python
- Use Flask when you specified FastAPI
- Create SQLite schemas when you need PostgreSQL

The context ensures **consistent tech stack** across all generated code.

### **7.3 Undo/Redo Stack**

```python
class ChangeHistory:
    def __init__(self):
        self.history = []
        self.current_index = -1
    
    def record_change(self, file_path, old_content, new_content):
        self.history.append({
            "file": file_path,
            "old": old_content,
            "new": new_content,
            "timestamp": datetime.now()
        })
        self.current_index += 1
    
    def undo(self):
        if self.current_index >= 0:
            change = self.history[self.current_index]
            write_file(change["file"], change["old"])
            self.current_index -= 1
    
    def redo(self):
        if self.current_index < len(self.history) - 1:
            self.current_index += 1
            change = self.history[self.current_index]
            write_file(change["file"], change["new"])
```

{test_output}

```python
    @tool
```

```python
def create_code_generator_tools(vfs: VirtualFileSystem) -> list:
    """Tools for code generator to communicate with planning agent."""
    
    @tool
    def report_completion(
        status: str,
        files_created: list[str],
        files_modified: list[str],
        notes: str = ""
    ) -> str:
        """Report task completion to planning agent.
        
        Args:
            status: 'completed', 'partial', or 'blocked'
            files_created: List of new files created
            files_modified: List of existing files modified
            notes: Any important notes or issues encountered
        """
        completion_data = {
            "status": status,
            "timestamp": datetime.now().isoformat(),
            "files_created": files_created,
            "files_modified": files_modified,
            "notes": notes,
            "ready_for_testing": status == "completed"
        }
        
        vfs.write_file(
            ".rudraanvil/completion_status.json",
            json.dumps(completion_data, indent=2)
        )
        return f"Reported {status} status to planning agent."
    
    @tool
    def log_progress(message: str) -> str:
        """Log your progress for the planning agent to monitor.
        
        Args:
            message: What you're currently doing
        """
        log_file = ".rudraanvil/logs/code_generation.log"
        timestamp = datetime.now().strftime("%Y-%m-%d %H:%M:%S")
        log_entry = f"[{timestamp}] {message}\n"
        
        current_log = vfs.read_file(log_file) or ""
        vfs.write_file(log_file, current_log + log_entry)
        
        return "Progress logged."
    
    return [report_completion, log_progress]
```

```python
def get_or_create_session_id(project_path: Path) -> str:
    """Get or create a session ID for this project."""
    session_file = project_path / ".rudraanvil" / "session_id.txt"

    session_id = hashlib.sha256(
        f"{project_path}-{datetime.now().isoformat()}".encode()
    ).hexdigest()[:12]
    
    session_file.parent.mkdir(parents=True, exist_ok=True)
    session_file.write_text(session_id)
    return session_id
```


## **The Problem with Built-in `write_todos`**

### **Why Your Plan Says "NEVER use write_todos"**

**The Issue:**
```python
# Agent calls write_todos
write_todos([
    {"task": "Create main.py", "status": "pending"},
    {"task": "Create auth.py", "status": "pending"},
    {"task": "Create tests.py", "status": "pending"},
    {"task": "Create models.py", "status": "pending"},
    {"task": "Create database.py", "status": "pending"},
    # ... 20 more tasks
])

# This entire list is stored in the LLM's MESSAGE HISTORY
# Every subsequent API call includes this full list
# 25 tasks × 50 tokens each = 1,250 tokens
# Repeated in EVERY message for the entire session
```

**Context Bloat:**
```
Message [0]: User: "Build FastAPI app"
Message [1]: Assistant: write_todos([...25 tasks...])  ← 1,250 tokens
Message [2]: Tool: "Todos written"
Message [3]: Assistant: "I'll start with main.py"
Message [4]: Tool: write_file("main.py", ...)
Message [5]: Assistant: write_todos([...25 tasks...])  ← ANOTHER 1,250 tokens
Message [6]: Tool: "Todos updated"
...

Total: 1,250 tokens × 10 updates = 12,500 tokens wasted!
```

## **Benefits of This Hybrid Approach**

### **1. Token Efficiency**

**Without hybrid:**
```
Project plan: 20 tasks × 50 tokens = 1,000 tokens
Repeated in every message × 50 messages = 50,000 tokens wasted
```

**With hybrid:**
```
Project plan: On filesystem (0 tokens in context)
Tactical plan: 4 tasks × 50 tokens = 200 tokens
Only in subagent context (isolated)
Total: 200 tokens (99.6% savings!)
```

### **2. Flexibility**

**Strategic plan (PLAN.md):**
- ✅ Stable, long-term
- ✅ Human can edit
- ✅ Persists across sessions

**Tactical plan (write_todos):**
- ✅ Dynamic, adapts to reality
- ✅ Agent can adjust on the fly
- ✅ Discarded when task complete

```
Planning Agent:
- Thinks strategically
```
